## 23. Java Memory Model (JMM)

## Senior-Level Topic

# 1. What is JMM?

<details>
<summary>Show Answer</summary>

**Answer:**

The **Java Memory Model (JMM)** is a formal specification that defines how threads **read and write shared memory**—what visibility, ordering, and atomicity guarantees exist when multiple threads access the same variables.

### Simple Definition

```text
JMM = rules for how thread memory interacts with main memory
Answers: "When does a write by Thread A become visible to Thread B?"
```

### JMM Memory Architecture

```text
┌─────────────────────────────────────────┐
│           Main Memory (Heap)            │
│     Shared variables live here          │
└──────────┬──────────────┬───────────────┘
           │              │
    ┌──────▼──────┐  ┌────▼────────┐
    │ Thread 1    │  │ Thread 2    │
    │ Working     │  │ Working     │
    │ Memory      │  │ Memory      │
    │ (CPU cache) │  │ (CPU cache) │
    └─────────────┘  └─────────────┘
```

### What JMM Specifies

| Aspect | JMM Defines |
|--------|-------------|
| **Visibility** | When writes are seen by other threads |
| **Ordering** | Which instruction reordering is allowed |
| **Atomicity** | Which operations are indivisible |
| **Happens-before** | Formal ordering relationships |

### Without JMM — Undefined Behavior

```java
// No JMM guarantees without sync/volatile
int x = 0;
boolean flag = false;

// Thread 1
x = 42;
flag = true;

// Thread 2
if (flag) {
    print(x); // could print 0, 42, or anything — unpredictable!
}
```

### JMM Tools in Java

```text
synchronized  → visibility + atomicity + ordering
volatile      → visibility + ordering (limited)
final         → visibility after construction
Atomic*       → visibility + atomicity via CAS
Thread.start/join → happens-before rules
```

**Interview Point:**

> JMM = formal spec for cross-thread memory behavior. Defines visibility, ordering, atomicity. Without JMM rules (sync/volatile) → unpredictable multi-threaded behavior.

</details>

# 2. Why JMM introduced?

<details>
<summary>Show Answer</summary>

**Answer:**

JMM was introduced in **Java 5** because early Java had **no formal memory model**—multithreaded programs behaved unpredictably on multi-core CPUs due to caching and compiler reordering.

### Problems Before JMM (Java 1.0–1.4)

```text
1. No visibility guarantees — writes could stay in CPU cache
2. Compiler freely reordered instructions for optimization
3. CPU reordered memory operations
4. Programs worked on single-core but broke on multi-core
5. "Write once, run anywhere" failed for concurrent code
```

### The Broken Flag Example

```java
// Pre-JMM — worked on single core, broken on multi-core
boolean done = false;

new Thread(() -> {
    while (!done) { } // infinite loop on multi-core!
}).start();

done = true; // other thread may never see this
```

### Why Not Just Use synchronized Everywhere?

```text
synchronized works but:
  - Heavy overhead for simple flags
  - Developers didn't know when it was needed
  - No formal rules → hard to reason about code
  - Needed lightweight alternatives (volatile, final rules)
```

### What JMM Solved

| Problem | JMM Solution |
|---------|--------------|
| Visibility | happens-before rules, volatile |
| Reordering | Memory barrier semantics |
| Portability | Same behavior on all JVM/OS/CPU |
| Predictability | Formal rules developers can follow |

### Java 5 Package

```text
JMM introduced alongside:
  volatile (enhanced semantics)
  java.util.concurrent (Atomic*, Lock, Executor)
  ConcurrentHashMap, BlockingQueue
  Formal happens-before specification
```

**Interview Point:**

> JMM introduced in Java 5 — multi-core CPUs exposed visibility/reordering bugs. Before JMM, concurrent code was unpredictable. JMM + volatile + j.u.c = modern Java concurrency.

</details>

# 3. Visibility problem?

<details>
<summary>Show Answer</summary>

**Answer:**

The **visibility problem** in JMM occurs when a thread writes a value to shared memory but **other threads continue reading a stale copy** from their working memory (CPU cache)—never seeing the update.

### How Visibility Breaks

```text
Thread A writes x = 10
  → value may stay in CPU cache (working memory)
  → NOT flushed to main memory

Thread B reads x
  → reads from its own CPU cache
  → gets old value x = 0

No error — silent wrong behavior
```

### Code Example

```java
class Shared {
    int x = 0;        // no volatile, no sync
    boolean ready = false;
}

Shared s = new Shared();

// Thread 1
new Thread(() -> {
    s.x = 100;
    s.ready = true;
}).start();

// Thread 2
new Thread(() -> {
    while (!s.ready) { } // may loop forever
    System.out.println(s.x); // may print 0 instead of 100
}).start();
```

### Visibility vs Atomicity

| Problem | Symptom | Example |
|---------|---------|---------|
| **Visibility** | Sees old value | Flag never becomes true |
| **Atomicity** | Partial update | count++ loses increments |
| **Ordering** | Wrong sequence | Sees flag before data |

### JMM Fixes for Visibility

```java
// Fix 1: volatile
volatile boolean ready = false;
volatile int x = 0;

// Fix 2: synchronized
synchronized void set() { x = 100; ready = true; }
synchronized void get() { return x; }

// Fix 3: AtomicReference
AtomicInteger x = new AtomicInteger(0);
```

### Happens-Before Creates Visibility

```text
If action A happens-before action B:
  All writes by A are visible to B

volatile write → happens-before → volatile read
unlock → happens-before → lock
thread.start() → happens-before → thread actions
```

**Interview Point:**

> Visibility problem = thread reads **stale cached value**. Core JMM problem. Fix: volatile, synchronized, Atomic classes — all establish happens-before.

</details>

# 4. Reordering problem?

<details>
<summary>Show Answer</summary>

**Answer:**

The **reordering problem** occurs when the compiler or CPU executes instructions in a **different order** than written in source code—causing other threads to observe state changes in an unexpected sequence.

### Source Code vs Actual Execution

```java
// Written in source code:
a = 1;
b = 2;
flag = true;

// CPU may actually execute:
b = 2;
flag = true;  // flag set before a=1!
a = 1;
```

### Dangerous Reordering Example

```java
int a = 0;
boolean flag = false;

// Thread 1
a = 42;       // (1)
flag = true;  // (2)

// Thread 2
if (flag) {   // (3) sees flag=true
    print(a); // (4) may print 0 — a=42 not yet visible!
}
// Reordering: (2) before (1) → Thread 2 sees flag but not a=42
```

### Who Reorders?

| Layer | Reorders For |
|-------|--------------|
| **Compiler (JIT)** | Optimization — eliminate redundant ops |
| **CPU** | Pipeline efficiency — out-of-order execution |
| **CPU cache** | Write buffering — delayed flush to main memory |

### As-If-Serial Rule

```text
Single thread: reordering allowed IF result identical
  for that thread alone

Multi-thread: reordering can break other threads' observations
  JMM restricts reordering at synchronization points
```

### JMM Prevents Harmful Reordering

```java
volatile boolean flag = false;
int a = 0;

// Thread 1
a = 42;       // (1) cannot move after (2)
flag = true;  // (2) volatile write — barrier

// Thread 2
if (flag) {   // (3) volatile read — barrier
    print(a); // (4) guaranteed 42
}
// volatile write (2) happens-before volatile read (3)
// (1) cannot be reordered past (2)
```

**Interview Point:**

> Reordering = compiler/CPU execute instructions out of order. Breaks multi-threaded assumptions. JMM restricts reordering at sync points (volatile, synchronized).

</details>

# 5. Happens-before rule?

<details>
<summary>Show Answer</summary>

**Answer:**

**Happens-before** is the central ordering rule of JMM—if action A happens-before B, then A's memory changes are **guaranteed visible** to B, and A appears to execute before B.

### Definition

```text
A happens-before B means:
  1. All writes by A are visible to B
  2. A is ordered before B (no reordering past this point)
  3. Transitive: A hb B, B hb C → A hb C
```

### All Happens-Before Rules

| Rule | Description |
|------|-------------|
| **Program order** | Each action in thread happens-before later action in same thread |
| **Monitor lock** | `unlock` on monitor happens-before next `lock` on same monitor |
| **volatile** | Write to volatile happens-before read of same volatile |
| **Thread start** | `thread.start()` happens-before any action in started thread |
| **Thread join** | All actions in thread happen-before `thread.join()` returns |
| **Thread interrupt** | `thread.interrupt()` happens-before interrupted thread detects it |
| **Finalizer** | Object constructor happens-before `finalize()` |
| **Transitivity** | A hb B and B hb C → A hb C |

### volatile Happens-Before

```java
int x = 0;
volatile boolean ready = false;

// Thread 1
x = 42;           // (1)
ready = true;     // (2) volatile write

// Thread 2
if (ready) {      // (3) volatile read — hb with (2)
    print(x);     // (4) sees x=42 — (1) hb (2) hb (3) → (1) visible at (4)
}
```

### synchronized Happens-Before

```java
synchronized (lock) {
    x = 10;  // write
}            // unlock — hb next lock

synchronized (lock) {
    print(x); // guaranteed 10
}            // lock
```

### No Happens-Before = No Guarantee

```java
// Regular variables — NO happens-before between threads
int x = 0;
x = 42;  // Thread 1 — no hb relationship
print(x); // Thread 2 — may see 0
```

### Transitivity Chains Visibility

```text
Thread A: x=1 → volatile write flag
Thread B: volatile read flag → y=2 → volatile write done
Thread C: volatile read done → print x, y

A's x=1 visible to C via: A→flag→B→done→C (transitive hb)
```

**Interview Point:**

> Happens-before = JMM's visibility + ordering guarantee. Memorize key rules: volatile write→read, unlock→lock, start→thread actions, thread actions→join. No hb = no guarantee.

</details>

# 6. Memory barriers?

<details>
<summary>Show Answer</summary>

**Answer:**

A **memory barrier** (memory fence) is a CPU/JVM instruction that **restricts memory reordering** and **forces cache flush/refresh**—implementing JMM happens-before semantics at the hardware level.

### What Memory Barriers Do

```text
1. Prevent instruction reordering across the barrier
2. Force flush of write buffer to main memory (store barrier)
3. Force refresh of cache from main memory (load barrier)
4. Implement happens-before semantics
```

### Types of Barriers

| Barrier | Effect |
|---------|--------|
| **Load barrier** | All reads after barrier see latest main memory values |
| **Store barrier** | All writes before barrier flushed to main memory |
| **Full barrier** | Load + Store — no reorder across it |

### How volatile Uses Barriers

```java
volatile boolean flag;

// Thread 1
a = 42;
flag = true;  // volatile write → STORE BARRIER inserted
              // a=42 flushed before flag=true published

// Thread 2
if (flag) {   // volatile read → LOAD BARRIER inserted
    print(a); // reads a from main memory — sees 42
}
```

### synchronized Uses Full Barrier

```java
synchronized (lock) {
    x = 10;
} // FULL BARRIER on unlock:
  // - all writes flushed to main memory
  // - prevents reordering past unlock

synchronized (lock) { // FULL BARRIER on lock:
    print(x);
} // - cache invalidated, reads from main memory
```

### Barrier in CPU Instructions

```text
x86:  mfence (full), sfence (store), lfence (load)
ARM:  dmb (data memory barrier)
JVM inserts appropriate barriers for volatile/sync
```

### Barriers vs Performance

```text
Barriers are expensive:
  - Flush CPU write buffer
  - Invalidate cache lines
  - Stall CPU pipeline

Why volatile is lighter than synchronized:
  - volatile: barrier on specific variable access
  - synchronized: full barrier + lock acquisition overhead
```

**Interview Point:**

> Memory barriers enforce JMM ordering at CPU level. volatile write = store barrier. volatile read = load barrier. synchronized = full barrier + lock. Hardware implementation of happens-before.

</details>

# 7. Instruction reordering?

<details>
<summary>Show Answer</summary>

**Answer:**

**Instruction reordering** is when the compiler or CPU executes instructions in a **different sequence** than the source code order—to improve performance, while preserving single-thread correctness.

### Who Reorders and Why

| Layer | Why Reorder |
|-------|-------------|
| **Compiler (JIT)** | Dead code elimination, constant propagation, loop optimization |
| **CPU** | Pipeline utilization — execute independent instructions in parallel |
| **Write buffer** | Delay memory writes — don't wait for main memory |

### Compiler Reordering Example

```java
// Source code
int a = 0;
int b = 0;

void method() {
    a = 1;
    b = 2;
    int c = a + b;
}

// Compiler may reorder to:
b = 2;    // independent — can move up
a = 1;
int c = a + b;
// Same result for single thread — reordering allowed
```

### CPU Out-of-Order Execution

```text
CPU sees:
  LOAD a
  ADD  1
  STORE a
  LOAD b

CPU executes independent LOAD b while waiting for LOAD a
  → instructions appear reordered to other cores
```

### Multi-Thread Danger

```java
// Thread 1 — may be reordered to: flag=true, then a=42
a = 42;
flag = true;

// Thread 2
if (flag) {
    print(a); // may print 0 — saw flag but not a=42
}
```

### JMM Restricts Reordering At

```text
volatile read/write   → no reorder across volatile access
synchronized enter/exit → no reorder across monitor boundary
final field write (constructor) → no reorder past constructor end
Atomic* operations    → no reorder across atomic op
```

### As-If-Serial Semantics

```text
Single thread: reordering OK if result identical for that thread
Multi-thread:  reordering can break other threads' observations
               JMM adds constraints at synchronization points
```

### DCL Singleton — Reordering Bug

```java
// WITHOUT volatile — reordering breaks singleton
instance = new Singleton();
// May publish reference BEFORE constructor completes!
// CPU reorders: allocate → assign ref → initialize (wrong order)

// WITH volatile — reordering prevented
private static volatile Singleton instance;
instance = new Singleton(); // safe — no reorder past volatile write
```

**Interview Point:**

> Compiler and CPU reorder for performance. Safe for single thread. Dangerous for multi-thread. JMM blocks reordering at volatile/sync boundaries. DCL needs volatile to prevent reordering.

</details>

# 8. CPU cache effects?

<details>
<summary>Show Answer</summary>

**Answer:**

**CPU cache effects** cause visibility problems because each CPU core has its own **L1/L2 cache**—writes by one thread may stay in the local cache and not reach main memory or other cores' caches immediately.

### Multi-Core Cache Architecture

```text
         Main Memory (RAM)
              ↑↓
    ┌─────────┼─────────┐
    │         │         │
 Core 1     Core 2     Core 3
 L1 Cache   L1 Cache   L1 Cache
 L2 Cache   L2 Cache   L2 Cache
    │         │         │
 Thread 1   Thread 2  Thread 3
```

### Cache Visibility Problem

```text
1. Thread 1 (Core 1): writes x=1 → stored in Core 1 L1 cache
2. Main memory still has x=0
3. Thread 2 (Core 2): reads x → reads Core 2 L1 cache → x=0 (stale!)
4. Thread 2 never sees x=1
```

### Cache Line

```text
CPU transfers data in cache lines (typically 64 bytes)
  Reading int x may load entire 64-byte cache line
  Writing int y in same line → invalidates line for other cores
  False sharing: unrelated variables in same cache line hurt performance
```

### False Sharing Example

```java
class Counters {
    volatile long count1 = 0; // same cache line as count2!
    volatile long count2 = 0;
}

// Thread 1 increments count1 → invalidates cache line
// Thread 2 increments count2 → invalidates cache line
// Constant cache line bouncing — severe performance hit
```

### Cache Coherence — MESI Protocol

```text
M = Modified   (only this core has it, main memory stale)
E = Exclusive  (only this core has it, matches main memory)
S = Shared     (multiple cores have same copy)
I = Invalid    (cache line invalid — must re-fetch)

When Core 1 writes:
  Other cores' copies marked Invalid
  BUT timing not guaranteed without volatile/sync
```

### How volatile Fixes Cache Issues

```java
volatile int x;

// Write: flush to main memory + invalidate other cores' cache lines
x = 42;

// Read: invalidate local cache + read from main memory
int val = x;
```

### Write Buffer Delay

```text
CPU doesn't wait for main memory on write:
  Write goes to store buffer (fast)
  CPU continues executing
  Store buffer flushed later (delayed)

Without volatile: other cores see write only after flush
With volatile: store buffer flushed immediately on volatile write
```

**Interview Point:**

> Each CPU core has local cache. Writes may not reach main memory → other threads see stale values. volatile/sync force cache flush. Watch false sharing on multi-core.

</details>

# 9. Compiler optimizations?

<details>
<summary>Show Answer</summary>

**Answer:**

The **JIT compiler** applies optimizations like **instruction reordering, dead code elimination, and register allocation** that can break multi-threaded visibility—JMM constrains these optimizations at synchronization boundaries.

### Common Compiler Optimizations

| Optimization | What It Does | Multi-Thread Risk |
|--------------|--------------|-------------------|
| **Reordering** | Move independent instructions | Other thread sees wrong order |
| **Dead code elimination** | Remove "unused" writes | Write never happens |
| **Register allocation** | Keep variable in CPU register | Never written to memory |
| **Loop optimization** | Cache loop variable in register | Other thread never sees updates |

### Dead Code Elimination Danger

```java
// Compiler may eliminate this write entirely!
boolean flag = false;

new Thread(() -> {
    while (!flag) { } // compiler sees flag never changes in THIS thread
}).start();

flag = true; // compiler may eliminate — "flag not read after this"
// Infinite loop — flag write removed as dead code!
```

```java
// Fix: volatile prevents elimination
volatile boolean flag = false; // compiler cannot eliminate volatile write
```

### Register Allocation Problem

```java
int x = 0;

new Thread(() -> {
    while (x == 0) { } // x cached in CPU register
}).start();

x = 1; // write to memory — thread may read from register forever
```

```java
// Fix
volatile int x = 0; // forces memory read/write, not register only
```

### Loop Optimization

```java
int i = 0;
while (i < 1000000) {
    i++; // compiler may optimize to run loop in register
    // other thread setting i=1000000 never seen
}
```

### JMM Constrains Compiler At Sync Points

```text
volatile read/write:
  Compiler cannot reorder across volatile access
  Cannot eliminate volatile reads/writes
  Cannot keep volatile variable in register only

synchronized:
  Compiler cannot move code out of synchronized block
  Cannot eliminate synchronized block

final:
  Compiler cannot reorder final field write past constructor end
```

### Happens-Before Guides Compiler

```text
Compiler respects happens-before edges:
  If A happens-before B → compiler cannot reorder A after B
  volatile write hb volatile read → no reorder across them
  unlock hb lock → no reorder across monitor boundary
```

### Optimization Example — Allowed vs Forbidden

```java
// ALLOWED by compiler (single thread same result):
a = 1;
b = 2;  // can move before a=1

// FORBIDDEN by JMM (volatile barrier):
a = 1;
flag = true;  // volatile write — a=1 cannot move after this
```

**Interview Point:**

> JIT compiler optimizes aggressively — reordering, dead code elimination, register caching. Breaks multi-thread without JMM constraints. volatile/sync tell compiler "don't optimize across this point."

</details>

### Q: JMM vs JVM memory areas?

<details>
<summary>Show Answer</summary>

**Answer:**

| | JMM | JVM Memory Areas |
|---|-----|------------------|
| What | Thread interaction rules | Physical memory layout |
| Defines | Visibility, ordering | Heap, Stack, Metaspace |
| Level | Specification/concept | Implementation |

JMM is about **how threads see shared data**. JVM memory areas are **where data is stored**.

</details>

### Q: final fields and JMM?

<details>
<summary>Show Answer</summary>

**Answer:**

JMM guarantees: **final field writes** in constructor happen-before any thread sees the object reference. Once object reference is visible, all final fields are guaranteed initialized.

```java
class Immutable {
    final int x;
    Immutable(int x) { this.x = x; } // final write in constructor
}
// Any thread seeing the object sees fully initialized final fields
```

</details>

### Q: Double-checked locking without volatile?

<details>
<summary>Show Answer</summary>

**Answer:**

**Broken** — compiler/CPU may reorder `instance = new Singleton()` to publish reference before constructor completes. Other thread sees partially built object. **volatile on instance field is mandatory** for safe DCL.
