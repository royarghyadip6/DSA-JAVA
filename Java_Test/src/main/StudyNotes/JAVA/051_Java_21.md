# 51. Java 21 Interview Questions

## 51. Java 21 Interview Questions

Java 21 is **LTS** — Virtual Threads (Project Loom), key for modern concurrency interviews.

## Modern Interviews

---

# 1. Virtual Threads?

<details>
<summary>Show Answer</summary>

**Answer:**

**Virtual threads** are **lightweight threads** managed by JVM — not 1:1 with OS threads. Millions can run concurrently.

```java
// Java 21
Thread.startVirtualThread(() -> {
    System.out.println("virtual thread: " + Thread.currentThread());
});

ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();
executor.submit(() -> processOrder(order));
```

```text
Platform thread: ~1 MB stack, OS-scheduled — thousands max
Virtual thread:  ~KB, JVM-scheduled — millions possible
```

**Interview Point:** Virtual thread = cheap thread. Use for high-concurrency I/O. Not for CPU-bound work.

</details>

# 2. Project Loom?

<details>
<summary>Show Answer</summary>

**Answer:**

**Project Loom** = OpenJDK project that brought **virtual threads** and related APIs to Java — lightweight concurrency without reactive complexity.

```text
Goals:
  ✅ Massive concurrency (millions of threads)
  ✅ Simple thread-per-request model returns
  ✅ No callback hell / reactive rewrite
  ✅ Structured concurrency APIs
```

Finalized in **Java 21 LTS**.

**Interview Point:** Loom = virtual threads in Java 21. Revives simple blocking code at scale.

</details>

# 3. Structured Concurrency?

<details>
<summary>Show Answer</summary>

**Answer:**

**Structured Concurrency** (Java 21 preview) — subtasks tied to parent scope — if parent fails/cancels, children are cancelled too.

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    Subtask<String> user = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));

    scope.join();
    scope.throwIfFailed();

    return new Dashboard(user.get(), orders.get());
}
```

```text
Parent scope owns child tasks — no orphaned threads
Failure in one → shutdown others
```

**Interview Point:** Structured concurrency = parent-child task lifetime bound. Prevents thread leaks from fire-and-forget.

</details>

# 4. Scoped Values?

<details>
<summary>Show Answer</summary>

**Answer:**

**ScopedValue** (Java 21) — immutable value scoped to a thread **and its child virtual threads** — alternative to ThreadLocal for virtual threads.

```java
private static final ScopedValue<String> USER = ScopedValue.newInstance();

ScopedValue.where(USER, "user-123").run(() -> {
    String user = USER.get(); // available in this scope
    processRequest();
});
// USER not available outside scope — auto cleaned
```

vs ThreadLocal — better for virtual threads (no pool leak risk).

**Interview Point:** ScopedValue replaces ThreadLocal for virtual threads — immutable, scoped, auto cleanup.

</details>

## Frequently Asked

# 5. Difference between Platform Thread and Virtual Thread?

<details>
<summary>Show Answer</summary>

**Answer:**

| | Platform Thread | Virtual Thread |
|---|-----------------|----------------|
| Maps to OS thread | 1:1 (mostly) | Many virtual → few carrier OS threads |
| Memory | ~1 MB stack | ~KB |
| Max count | Thousands | Millions |
| Best for | CPU-bound | I/O-bound (HTTP, DB) |
| Blocking I/O | Blocks OS thread | Blocks virtual thread only — carrier released |
| `Thread.currentThread()` | Platform or virtual | Both work |

```text
Virtual thread blocked on I/O → JVM mounts another virtual thread on carrier
```

**Interview Point:** Platform = OS thread. Virtual = JVM-managed, cheap. I/O blocking doesn't pin OS thread with virtual threads.

</details>

---

# 6. Why Virtual Threads introduced?

<details>
<summary>Show Answer</summary>

**Answer:**

```text
Problem: 10,000 concurrent HTTP requests
  Platform threads: need 10,000 OS threads — OOM or thrashing
  Reactive (WebFlux): complex, callback hell, harder debugging

Solution: Virtual threads
  10,000 virtual threads on ~CPU count carrier threads
  Write simple blocking code — scales like reactive
```

**Interview Point:** Virtual threads solve C10K with simple blocking code — no reactive rewrite needed.

</details>

---

# 7. Millions of threads possible?

<details>
<summary>Show Answer</summary>

**Answer:**

**Yes** for **I/O-bound** workloads — virtual threads are cheap (KB vs MB).

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            Thread.sleep(1000); // simulated I/O
            return 1;
        });
    }
}
```

**Not** for CPU-bound — still limited by CPU cores. Pinning carrier (synchronized, native code) reduces benefit.

**Interview Point:** Millions of virtual threads for I/O wait. CPU-bound still needs platform threads or parallel streams.

</details>

# 8. Virtual Thread vs ExecutorService?

<details>
<summary>Show Answer</summary>

**Answer:**

| | Fixed ThreadPool | Virtual Thread Executor |
|---|------------------|-------------------------|
| Thread type | Platform | Virtual |
| Pool size | Bounded (e.g. 200) | Unbounded virtual threads |
| Queue | Bounded queue + rejection | No traditional queue limit |
| Use case | CPU + moderate I/O | Massive I/O concurrency |

```java
// Old — bounded
ExecutorService pool = Executors.newFixedThreadPool(200);

// Java 21 — virtual
ExecutorService virtual = Executors.newVirtualThreadPerTaskExecutor();
```

**Interview Point:** newVirtualThreadPerTaskExecutor() — one virtual thread per task. Don't pool virtual threads like platform threads.

</details>

---

# 9. Performance impact?

<details>
<summary>Show Answer</summary>

**Answer:**

| Workload | Virtual Threads |
|----------|-----------------|
| **I/O-bound** (REST, DB) | ✅ Major improvement — higher throughput |
| **CPU-bound** | ❌ No benefit — use parallel streams/platform pool |
| **Pinning** (synchronized in hot path) | ⚠️ Degrades — carrier blocked |

```text
Avoid: synchronized blocks in virtual thread code — use ReentrantLock
Avoid: thread-local heavy patterns without ScopedValue
Monitor: carrier thread pool size (default = CPU cores)
```

**Interview Point:** Virtual threads win on I/O. Pinning synchronized blocks hurts. Profile before/after migration.

</details>

# 10. Migration strategy?

<details>
<summary>Show Answer</summary>

**Answer:**

```text
1. Upgrade to Java 21
2. Replace Executors.newFixedThreadPool with newVirtualThreadPerTaskExecutor for I/O tasks
3. Spring Boot 3.2+: spring.threads.virtual.enabled=true
4. Replace synchronized with ReentrantLock in hot paths (avoid pinning)
5. Replace ThreadLocal with ScopedValue where needed
6. Load test — compare throughput under concurrent I/O
7. Keep platform threads for CPU-bound batch jobs
```

```yaml
# Spring Boot 3.2+
spring:
  threads:
    virtual:
      enabled: true
```

**Interview Point:** Enable virtual threads in Spring Boot 3.2+. Audit synchronized/native pinning. Load test I/O paths.

</details>
